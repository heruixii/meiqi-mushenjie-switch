## 4. 翻译表规范

主表使用 UTF-8 with BOM、TSV 格式。主要字段：

```text
id
file
length_offset
text_offset
source
translation
control_codes
status
notes
```

### 4.1 ID 规则

ID 通常是：

```text
Script/scenario01_1.binu8@81741
Config/event.datu8@72
```

其中 `@` 后为文本在资源中的偏移位置。ID 是唯一定位依据，不能用翻译表行号代替。

任何批次文件至少应包含：

```text
id<TAB>translation
```

合并前必须确认：

- ID 存在于主表
- 批次中没有重复 ID
- 目标记录没有被其他译文占用
- 译文不为空
- 没有误改 `source`

### 4.2 文本类型

必须把以下类型分开：

1. 剧情对白和旁白。
2. 角色名、语音关联文本。
3. 选项、章节标题、回想标题。
4. 系统菜单、按钮、提示和帮助文字。
5. 演出控制字符串。
6. 内部变量、文件名、资源 ID 和函数注释。

只有前四类通常属于玩家可见汉化范围。第五类只有在确实显示给玩家时才处理。第六类默认保留原文，避免改变引擎逻辑。

### 4.3 翻译状态

推荐状态：

```text
未翻译
初译完成
术语检查
PC版替换待抽检
人工润色
已导入
已实机验证
内部字符串-无需翻译
```

不要为了让统计看起来完整，把内部变量强行翻译成中文。不要把 PC 替换自动标记成“人工润色”。

## 5. PC 汉化安全替换规则

这是本项目最重要的规则。

### 5.1 允许的匹配方式

PC 汉化内容只能按以下信息联合匹配：

```text
场景文件
＋ PC 原版原文
＋ PC 汉化版对应译文
＋ 语音编号（存在时）
```

有语音标记时，优先按场景和语音编号匹配。没有语音标记时，要求 PC 原版和 PC 汉化脚本在同一场景结构中对应，并且标准化后的译文唯一。

### 5.2 禁止的匹配方式

禁止：

- 按所有场景的全局顺序套用。
- 只按原文字符串全局替换。
- 只按行号替换不同版本脚本。
- 相同短句存在多个候选译文时强行选择。
- 用 PC 文本覆盖人工润色 ID。
- 未确认版本就混用不同 PC 或 Switch 资源。

全局顺序替换曾经会导致串台，是明确禁止的方案。

### 5.3 标准化范围

匹配时可以标准化：

- PC 与 Switch 的换行表示，例如 `[r]` 和 `@n`
- 外层引号
- 语音标记
- 不影响语义的多余空白

不能标准化掉：

- 人名
- 实际对白文字
- 否定、时态和语气
- 角色标记
- 有意义的特殊符号

同一场景中出现相同原文但不同译文时，必须跳过并记录为冲突；不要为了增加替换数量而冒险替换。

### 5.4 人工润色保护

人工润色的 ID 受到保护。批量 PC 替换、机器翻译、简繁转换和自动修复都不能覆盖人工润色，除非用户明确指定某个 ID 重新修改。

每次批量操作后必须输出：

```text
人工润色保护数量
被覆盖数量（必须为 0）
成功替换数量
冲突数量
跳过数量
控制码新增错误数量
```

## 6. 翻译和人工润色规范

### 6.1 翻译目标

目标语言为简体中文。译文应符合视觉小说语境，优先保证：

- 剧情含义准确
- 说话人明确
- 角色性格和语气稳定
- 人名、组织名和称呼统一
- 伏笔、双关和上下文不被机械直译破坏
- 中文自然，不保留明显机翻句式

### 6.2 角色和术语

角色名应参考 PC 汉化使用的名称，除非用户明确要求更改。处理角色名时同时检查：

- 对白中的称呼
- 角色名栏
- 语音关联标记
- 章节标题和回想标题
- 系统角色列表

不要只替换角色名表而不检查对白中的称呼。

### 6.3 润色顺序

人工润色应按场景连续阅读：

```text
读取同场景前后文
→ 确认说话人
→ 确认剧情语境
→ 检查术语和称呼
→ 调整中文语序和语气
→ 保留控制码
→ 检查文本框长度
```

不要孤立地把每句译文改得很漂亮，却破坏前后文的称呼、时态和语气。

### 6.4 长文本

长文本要优先检查：

- 是否保留 `@n` 换行
- 是否有多余或缺失换页
- 是否超过文本框宽度
- 是否出现一整段挤在一行
- 是否出现控制码显示为普通文字
- 是否因简体字宽度变化导致最后一行被截断

中文译文不应简单按照日文字符数等比例压缩。必要时在不破坏控制码的前提下重排句子或增加合法换行。

## 7. 字体处理规范

### 7.1 已知问题

日文游戏字体不一定包含简体中文字符。曾出现过汉字显示为空白的情况，原因是实际加载字体的字形映射和覆盖范围不足，而不是翻译表没有内容。

因此看到某个字消失时，优先检查：

1. 译文是否真的写入资源。
2. 文本编码是否正确。
3. 游戏实际加载的是哪一个 TTC 字体。
4. TTC 的 cmap 是否包含该简体字。
5. 字形是否已加入字体但索引没有映射。
6. 字体文件是否被补丁正确覆盖。

### 7.2 字体流程

```text
收集翻译表中的所有字符
→ 扫描游戏 TTC 字体 cmap
→ 输出缺字列表
→ 添加简体字形或 cmap 别名
→ 构建字体覆盖文件
→ 单独测试常用字和标点
→ 再进行全文构建
```

重点测试：

```text
世界、真相、丑陋、之间、间、界
章节标题
角色名
中文标点
数字和英文
```

不要只测试“你好世界”后就认为字体完成；实际剧情中出现的每个简体字都需要覆盖检查。

### 7.3 字体相关脚本

```text
06_scripts\analyze_fonts.py
06_scripts\report_missing_glyphs.py
06_scripts\patch_ttc_cmap_aliases.py
06_scripts\add_ttc_glyphs.py
06_scripts\normalize_simplified.py
```

字体改动必须生成新构建，不要直接替换正式补丁中的 TTC 文件。

## 8. 批量翻译工作流

### 8.1 开始前

先读取：

```text
03_text\translated\translation-sheet.tsv
03_text\glossary\人物名表.csv（若存在）
docs\08_character-name-reference.md
docs\01_current-findings.md
```

确认当前表的记录数、状态分布、最近修改时间和备份文件。

### 8.2 制作批次

批次建议按以下范围之一：

- 单个场景
- 同一幕的连续场景
- UI 的一个功能组
- 150 条左右的连续剧情记录

每批都要保留原 ID，不得重新编号。批次文件应放入 `03_text\translated`，文件名写清场景、批次和处理方式，例如：

```text
第六幕场景03-auto-batch01.tsv
第三幕场景04-manual-batch01.tsv
界面文字-batch01.tsv
```

### 8.3 合并前检查

检查：

- 译文是否为空
- 是否混入繁体字
- 是否有假名残留
- 是否保留语音标记
- 是否保留 `@n`、`@r` 等控制码
- 是否有批次重复 ID
- 是否误翻译内部资源名
- 是否包含不属于该场景的文本

### 8.4 合并后

合并后立即保存主表备份：

```text
translation-sheet.before-<批次名>.tsv
```

不要在没有备份的情况下连续合并多个批次。每个批次成功后再进入下一批。

## 9. 常用脚本和使用方式

所有脚本从历史项目目录执行。推荐使用项目自带 Python：

```text
冥契汉化历史文件\.venv\Scripts\python.exe
```

如果环境已经移动或虚拟环境失效，先检查 Python 和依赖，不要直接修改脚本中的路径。

### 9.1 提取 BINU8/DATU8 字符串

```powershell
python 06_scripts\extract_binu8_strings.py 01_extracted\romfs --output 03_text\extracted\strings.tsv
```

默认扫描：

```text
Script/*.binu8
Config/*.datu8
```

需要扫描全部文件时可加 `--all`。提取结果只用于分析，不等于所有字符串都应该翻译。

### 9.2 合并普通翻译批次

```powershell
python 06_scripts\merge_translation_batch.py `
  03_text\translated\translation-sheet.tsv `
  03_text\translated\某批次.tsv `
  --output 03_text\translated\translation-sheet.after-某批次.tsv
```

确认输出无误后，才将输出作为下一阶段主表。若批次 ID 不存在、重复或原译文冲突，脚本应停止；不要绕过错误强行写入。

### 9.3 简繁转换

只有在确认目标字段需要转换时使用：

```powershell
python 06_scripts\normalize_simplified.py `
  --master 03_text\translated\translation-sheet.tsv `
  --names 03_text\glossary\人物名表.csv `
  --glossary 03_text\glossary\术语表.csv
```

简繁转换前必须备份。自动转换可能改变专名、异体字、角色名或用户刻意保留的写法，不能代替人工检查。

### 9.4 PC 语音文本安全匹配

脚本参数：

```text
apply_pc_voice_translations.py sheet pc_root backup
```

使用前必须确认：

- `pc_root` 是 PC 原版场景脚本根目录
- PC 脚本和 Switch 版本对应
- `backup` 是新的备份文件路径
- 主表已关闭，没有被 Excel 占用

### 9.5 PC 全量安全匹配

脚本参数：

```text
apply_pc_full_safe.py sheet pc_original_root pc_patch_root backup
```

语义：

```text
sheet             当前 Switch 翻译表
pc_original_root  PC 原版 scenario*.ks 所在目录
pc_patch_root     PC 汉化后 scenario*.ks 所在目录
backup            执行前备份路径
```

该脚本的安全条件是“同场景、同原文、PC 译文唯一”。不满足条件的记录必须跳过。

不要将 PC 汉化目录中的 `data.xp3`、可执行文件或完整版权资源复制到发布目录。

### 9.6 修复自动翻译控制码

```powershell
python 06_scripts\repair_batch_controls.py 批次.tsv 03_text\translated\translation-sheet.tsv
```

该脚本只适合修复确认过的批次文件。修复后必须再次比较源文本与译文的控制码集合。不能把控制码当作普通文字让翻译模型自由改写。

### 9.7 构建 LayeredFS 补丁

```powershell
PowerShell -ExecutionPolicy Bypass -File 06_scripts\build_layeredfs.ps1 `
  -TranslationSheet 03_text\translated\translation-sheet.tsv `
  -Output 07_build\新版本名
```

构建脚本会：

1. 根据翻译表生成 `Script` 和 `Config` 覆盖文件。
2. 处理字体 cmap 别名。
3. 将翻译表中的字符加入游戏字体。
4. 输出 `atmosphere\contents\01003080177CA000\romfs`。

新的输出目录不能覆盖旧版本。正式版本应使用新名称，例如 `pc-merged-v484`，确认通过后再复制到发布目录。

## 10. 自动质量检查

每次构建前后至少检查以下项目。

### 10.1 翻译表检查

- 总记录数没有异常变化。
- ID 唯一。
- `source` 没有被改写。
- 剧情和 UI 译文不为空。
- 状态数量变化符合本批次预期。
- 人工润色保护 ID 数量没有减少。
- 没有突然增加大量繁体字。
- 没有新出现假名日文。

### 10.2 控制码检查

逐条比较 source 和 translation 的控制码，至少包括：

```text
@n
@r
@v角色_编号
@r字@丶 等强调结构
换页、等待、颜色和字体标签
```

控制码数量或顺序变化时，不能直接构建发布版。先定位具体 ID。

### 10.3 文件检查

确认：

- 正式补丁存在 `atmosphere`。
- Title ID 为 `01003080177CA000`。
- `romfs\Config`、`romfs\Script`、`romfs\System` 路径正确。
- 没有把整个本体复制进补丁。
- 没有加入 `prod.keys`、PC 可执行文件或开发环境。
- 没有混入旧版本的部分文件。

### 10.4 日文残留检查

日文残留检查要分两类：

1. 玩家可见文本字段中的平假名、片假名和明显日文句子。
2. 内部脚本变量、资源名、文件名和注释。

第一类若存在，需要处理或确认是有意保留。第二类通常不应修改。不能仅凭整个二进制文件中搜到日文就判定补丁漏译。

## 11. 抽样检查方案

抽样必须可复现。记录：

```text
抽样数量
随机种子
筛选条件
检查日期
检查人/智能体
发现的问题
```

建议分层抽样：

- PC 汉化替换文本
- 人工润色文本
- 初译文本
- 每一幕至少若干条
- 分支场景
- 系统菜单和按钮
- 章节标题
- 长文本
- 含控制码文本

每条抽样至少核对：

- 场景是否一致
- 角色是否一致
- 原文含义是否对应
- 译文是否自然
- 人名和术语是否统一

- 是否可能超出文本框

## 12. Switch 实机测试

实机测试需要用户把正式补丁中的 `atmosphere` 复制到虚拟系统 SD 卡根目录；智能体不能替用户操作物理 SD 卡。

推荐测试路径：

```text
关闭游戏
→ 备份当前存档
→ 复制 atmosphere 到 SD 根目录并合并
→ 启动虚拟系统
→ 启动游戏
→ 检查标题画面
→ 开始新游戏
→ 检查章节标题和角色名
→ 推进长对白
→ 测试选项和分支
→ 测试自动、快进、回看、语音
→ 测试设置菜单和按钮
→ 测试存档、读档、快速存档
→ 重启游戏
```

重点观察：

- 中文是否显示为空白或方框。
- “界”“间”等简体字是否显示。
- 章节标题是否完整。
- 角色名是否被截断。
- 长句是否溢出文本框。
- `@n` 等控制码是否错误显示。
- 语音与对白是否错位。
- 选项是否重叠或无法选择。
- 回想、事件和分支是否能正常进入。
- 游戏是否在某个场景崩溃。

实机问题记录格式：

```text
日期：
补丁版本：
游戏版本：
场景/菜单：
复现步骤：
实际结果：
预期结果：
截图或视频：
严重等级：阻断/严重/一般/排版
```

若出现启动失败或关键场景崩溃，立即移除补丁并回退到上一个已知可运行版本，不要继续叠加修改。

## 13. 正式发布流程

正式发布前：

1. 读取主表和最近验证表。
2. 生成新的构建版本，不覆盖旧版本。
3. 检查 Title ID 和目录结构。
4. 检查控制码、字体和日文残留。
5. 做分层随机抽样。
6. 在 Switch 上实机回归。
7. 将通过的构建复制到 `汉化补丁\09_release`。
8. 更新 `使用方法.md` 中的版本信息。
9. 更新 `恢复日文方法.md`，确认路径仍准确。
10. 重新制作发布压缩包。
11. 从全新临时目录解压压缩包，验证压缩包可用。

发布压缩包只能包含：

```text
正式补丁目录
使用方法.md
恢复日文方法.md
```

不能包含：

- 原版 NSZ/NCA/RomFS
- `prod.keys`
- PC 原版或 PC 汉化完整资源
- 翻译表和人工润色数据
- `.venv`
- 历史构建
- 调试日志中的敏感本地路径

## 14. 恢复日文和回退

用户恢复日文时，只处理对应 Title ID：

```text
SD:/atmosphere/contents/01003080177CA000/
```

删除或移除汉化补丁提供的覆盖目录即可。不要删除：

- 其他 Title ID 的补丁
- Nintendo 系统目录
- 用户存档目录
- 与本项目无关的 Atmosphere 文件

恢复日文不会删除存档；但任何存档操作前都建议用户自行备份。

开发端回退时优先使用 `03_text\translated` 中最近一次正确备份，或 `08_test\历史构建` 中上一个已知可运行构建。不要使用破坏性 Git 命令或直接删除整个历史目录。

## 16. 常见误判和处理方式

### 16.1 看到 7,303 条未翻译

不要马上继续机器翻译。先按文件和文本类型分类。大部分是内部字符串、变量和资源标识，不属于可见剧情。

### 16.2 看到某个字为空白

不要立即改译文。先检查字体 cmap、实际加载的 TTC、字形覆盖和补丁路径。曾经的“界/间”问题属于字体显示链问题。

### 16.3 PC 译文看起来更完整

不要按行号或全局顺序替换。使用 `apply_pc_full_safe.py` 的场景级唯一匹配；有歧义就跳过。

### 16.4 翻译表行数变了

先比较 ID 集合和文件大小。行数变化可能来自重新提取、重复记录或换行解析错误，不能直接合并。

### 16.5 出现繁体字

先确认是译文、角色名、术语表还是原文/内部字段。只对目标中文字段做简体转换，转换前备份。

### 16.6 构建成功但游戏异常

构建成功只说明文件生成成功，不代表游戏运行正确。优先检查：

```text
控制码
编码
文本长度
字体覆盖
文件路径
Title ID
版本对应关系
```

## 18. 当前推荐行动

项目目前不应重新处理已经完成的 PC 安全替换。下一步应根据用户实际需要选择：

```text
实机发现问题
→ 按截图和场景定位
→ 修正单个或一组 ID
→ 自动检查
→ 新版本构建
→ 回归测试
```

如果没有新的实机问题，优先做正式补丁的独立安装验证、恢复日文验证和发布压缩包完整性验证，而不是对内部“未翻译”记录继续翻译。

## 19. 文件修改纪律

必须：

- 使用补丁或结构化脚本修改文件。
- 保留原文和 ID。
- 每次批量修改前备份。
- 每次修改后自动检查。
- 生成新版本而不是覆盖旧版本。
- 对用户说明实际修改了哪些文件。

禁止：

- 直接覆盖原版本体。
- 直接编辑正式发布补丁作为唯一来源。
- 使用全局顺序套用 PC 汉化。
- 覆盖人工润色内容。
- 把内部字符串计入剧情漏译。
- 未验证控制码就构建。
- 将密钥、原版资源或 PC 完整资源放入发布包。
- 使用 `git reset --hard`、`git checkout --` 等方式丢弃用户资料。

## 20. 交接结论

本项目的核心经验可以概括为：

```text
先分类，再翻译
先锁定 ID，再合并
先按场景匹配，再使用 PC 参考
先保护人工润色，再做批量操作
先处理字体覆盖，再判断缺字
先自动验证，再实机测试
先生成新版本，再替换正式发布版
```

任何后续智能体都应把这套顺序作为默认工作流。
